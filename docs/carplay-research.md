# CarPlay sender research and experimental diagnostics

Status: discovery and read-only RTSP diagnostics only. No session establishment, video, audio, remote input, Bluetooth handoff or wired CarPlay is implemented. A successful `/info` response is not evidence of CarPlay support. No physical device or receiver has been tested.

## Evidence inspected

- Cafari [build 881](https://github.com/rPlayAI/cafari-public/releases/tag/v152.0.7956.881), downloaded from the public release and supplied by the user. Both copies have SHA-256 `ac0bc3f6418b05fffc4855c62187be86fc0a69c16963022d25d0e82dda4ee4f5`, matching GitHub's release metadata. Its main binary is arm64 Mach-O, LC_ENCRYPTION_INFO_64 `cryptid=0` (not FairPlay-encrypted). Inspection included plist and extension metadata, Mach-O load commands/symbol table, strings and a Capstone disassembly of the exported `_AirPlaySenderClientConnectByIP` entry point. Function names and log strings are evidence of code paths, not proof of how a particular receiver behaves.
- Objective-C method-name metadata includes `beginScreenBroadcastToReceiver:`, `presentScreenBroadcastStarter`, `setCarPlayReceiver:` and `pressBroadcastPicker`. These identify app interfaces, not a verified head-unit input implementation.
- The bundle declares `_airplay._tcp` and `_raop._tcp` Bonjour services; it links CarPlay, ReplayKit, VideoToolbox, AVFoundation and Network frameworks and contains a `com.apple.broadcast-services-upload` extension. The binary contains `GET /info RTSP/1.0`, `/auth-setup`, `/pair-setup`, `/pair-verify`, `/fp-setup`, `/info`, SETUP, RECORD, `requestUI`, `disableBluetooth`, `streamConnectionID`, `hidSendReport`, VideoToolbox H.264 profile and compression-session symbols. A diagnostic string describes `CarPlay MFi-SAP (encryptType=0, FairPlay off, no PIN)`, but that does not establish universal authentication requirements or prove FairPlay and MFi are interchangeable.
- Binary diagnostics refer to initial session SETUP, /info, a screen SETUP, event port, requestUI, audio stream type 102, timing, and a Bluetooth handoff wait. Other strings describe both AES and ChaCha branches. These are not a complete wire capture or a verified end-to-end recipe. No receiver address, universal port, transport encryption policy, or binary protocol fixture was established from these strings.
- Cafari's [issue 3](https://github.com/rPlayAI/cafari-public/issues/3) describes a BMW where initial SETUP succeeded but a resolution reconnect after Bluetooth handoff failed. This is a reported failure, not proof of cause, and is a different head unit from the requested portable display.
- [CatPlay Bonjour](https://github.com/catplay-labs/catplay/blob/master/carplay/catplay_carplay/src/common/bonjour_entry.rs) identifies `_airplay._tcp.local.` and fields including `model`, `features`, `flags`, `deviceid`, `pi` and `pk`. [CatPlay transmitter bootstrap](https://github.com/catplay-labs/catplay/blob/master/carplay/catplay_carplay/src/carplay_tx/transmitter.rs) describes pairing/authentication branches, initial SETUP, /info, event/timing and keepalive. Its [RTSP client](https://github.com/catplay-labs/catplay/blob/master/carplay/catplay_carplay/src/carplay_tx/client.rs) and [stream setup](https://github.com/catplay-labs/catplay/blob/master/carplay/catplay_carplay/src/carplay_tx/transmitter_impl.rs) document subsequent SETUP, RECORD, screen TCP and audio. CatPlay describes firmware for hardware with an MFi chip; those receiver requirements cannot be assumed for a phone-side sender. Its sender is Rust with substantial dependencies; no code has been copied or linked. Verify licence and iOS portability before reuse.
- [Cafari Lite](https://github.com/rPlayAI/cafari-lite) is the separate native CarPlay scene and explicitly requires an Apple-granted entitlement. [CarCast](https://github.com/rPlayAI/carcast-public) is a receiver with source unavailable in that repository. [rPlayHub](https://github.com/rPlayAI/rPlayHub) uses a trusted external host and CoreDevice, not a native CarPlay sender.

## Capture and iOS constraints

Cafari's extension demonstrates a ReplayKit broadcast-upload approach in this build, not that Kite can silently capture other apps. Apple's current [ScreenCaptureKit documentation](https://developer.apple.com/documentation/ScreenCaptureKit) describes a system picker, usage description and sample buffers, but runtime availability, entitlements, consent, sideload signing and background lifetime on the specific iOS 27.0 device remain unverified. [Local network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) requires user permission and declared Bonjour types. Do not assume a different app's touch events can be injected or DRM-protected frames captured.

## In this branch

Settings > Receiver diagnostics discovers `_airplay._tcp` services on the currently connected network and allows a user-selected read-only TCP `GET /info` probe, either via Bonjour or a manually supplied host and port. Many AirPlay services are not CarPlay devices. Some compatible receivers may reject an unauthenticated /info before SETUP; a failure is not proof of incompatibility. The probe times out, bounds reply sizes, closes connections, and never sends SETUP, changes Bluetooth, streams media or claims a session. It does not join Wi-Fi or assume a fixed address/port.

The local encoder test produces a single synthetic H.264 frame with VideoToolbox, collecting AVCC bytes and SPS/PPS. It does not send video to a receiver. `H264TestPatternTests` checks the resulting parameter-set types and invalid frame sizes. Hardware and live-stream performance remain unverified.

`ReceiverProbeTests` exercises incremental framing, binary payloads, status, malformed headers, duplicate lengths and size limits. These are parser tests, not hardware or full-protocol integration tests. The branch CI builds a separately labelled diagnostics IPA artifact; see its Actions run. It is ad-hoc signed and must be re-signed when sideloaded, without implying any CarPlay entitlement.

## Outstanding work

Acquire a consented capture from the exact portable head unit, including discovery TXT, session sequence, response payloads and media ports with secrets and personal data removed. Establish receiver-specific authentication and authorization, then implement and test SETUP/event/timing/feedback/TEARDOWN and encryption. Define video frame headers and codec configuration, sequence/timing and resolution; implement real-time H.264 encode and compare with a mock and receiver. Implement HID input, audio, lifecycle, reconnect and safe conflict handling. Test Wi-Fi switching and real hardware, and study wired transport independently. An encoder or an `/info` reply alone is not a working sender. No Apple-issued CarPlay entitlement is requested by this prototype; that alone does not establish that an entitlement-free complete sender is possible on this hardware.
